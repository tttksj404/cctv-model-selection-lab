# 기능 명세서

> 문서 구분: 이 문서는 최종 제품의 목표 기능과 구현 계획을 정의한다. 현재 구현 완료 목록이 아니며, 실제 호출 가능한 계약은 [REST API 명세서](<./API 명세서.md>)의 현재 제공 API와 `dev` 코드를 기준으로 확인한다. Tailscale, 카메라 4대 동시 탐색, AI Worker 자동 작업, 경로 예측 및 WebSocket/STOMP 알림은 별도 완료 표시가 없는 한 목표 또는 후속 구현 범위다.

역할:

- 임베디드
- 백엔드
    - 보안(회원 관리) → 윤현준, 김성진, 안혜민
    - 통신 → 박하민
    - DB, 인프라(영상 저장, 배포) → 안혜민
    - REST API, 프론트 같이(대시보드 구성) → 윤현준
    - AI → 김성진
    - 로그, 테스트 → 모두가 형식을 맞춰서 해야 함.

| RE-SF1 | 회원 및 권한 관리 | 관제실 관리자의 계정과 시스템 접근 권한을 관리한다. 신고자는 회원 계정을 만들지 않는다. |   • 관리자는 사전 생성된 계정과 ADMIN 세션으로 로그인한다.
  • 사건 등록·수정·상태 변경·종료는 ADMIN 세션과 CSRF 토큰을 요구한다.
  • 신고자는 사건조회번호와 전화번호로 최소 진행 상태만 조회한다. |
| RE-SF2 | 실종 신고 및 사건 관리 | 관리자가 실종 신고를 사건으로 등록하고 인상착의, 사진, 마지막 목격 위치·시각을 통합 관리한다. |  1. 사건 접수
  • 관리자 대시보드에서 신고자 스냅샷, 실종자 정보, 구조화 인상착의와 마지막 목격 정보를 입력한다.
  • 사건 기본 정보는 JSON API로 등록하고 선택 사진은 별도 사진 API로 업로드한다.

2. 데이터 저장
  • 사건 정보와 신고자 정보는 MySQL에 저장한다.
  • 실종자 사진은 MinIO 객체 저장소에 저장한다.
  • 파일 저장 경로와 파일 정보는 MySQL에서 관리한다.

3. 사건 상태 관리
  • 사건은 접수, 탐색 중, 후보 발견, 종료 등의 상태로 구분한다.
  • 관리자가 사건 내용을 조회하고 상태를 변경할 수 있도록 한다.
  • 접수·후보 발견·수색 중 상태에서 탐색 중으로 진입할 때마다 실시간 사용 가능 조건 1개와 활성 사건 카메라 1대 이상을 서버에서 검증한다.
  • 탐색 중 진입은 실시간 검색 대상 변경 알림을 발행하지만 녹화 분석 작업을 자동 등록하지 않는다. |
| RE-SF3 | 실종자 탐색 조건 관리 | 신고 정보를 바탕으로 자연어 인상착의, 탐색 시간대, CCTV 및 구역 등 사건별 탐색 조건을 설정한다. |  1. 인상착의 조건
  • 사건 상세의 실시간 탐색 설정 카드에서 탐색 조건과 사건별 카메라를 함께 관리한다.
  • 조건은 성별(사람·남성·여성), 상의 색, 소매 길이와 하의 색을 구조화 입력받고 생성될 영어 canonical prompt를 저장 전에 표시한다.
  • 상·하의 색은 `black`, `blue`, `brown`, `green`, `gray`, `orange`, `pink`, `purple`, `red`, `white`, `yellow`, 소매 길이는 `short sleeve`, `long sleeve`만 지원한다.
  • 제외 조건은 선택 사항이지만 활성화하면 주 조건과 같은 구조를 모두 입력한다.
  • 유사도 임계값은 관리자 화면과 중앙 서버의 탐색 조건에서 설정하지 않는다.

2. 텍스트 특징 생성
  • 서버는 신규·수정 조건을 canonical prompt로 정규화하며 실패하면 저장을 거부한다.
  • 응답의 `normalizedPrompt`, `normalizedExclusionPrompt`, `realtimeUsable`로 정규화 결과와 실시간 사용 가능 여부를 제공한다.
  • 레거시 비정규 조건은 조회하되 준비 조건에 포함하지 않고, 관리자가 구조화 입력으로 다시 저장하도록 안내한다.
  • 정규화된 인상착의는 CLIP 텍스트 인코더를 이용하여 특징 벡터로 변환한다.
  • 생성된 특징 벡터는 녹화 영상 및 실시간 영상의 후보 유사도 비교에 사용한다.

3. 탐색 범위 설정
  • 마지막 목격 시각을 기준으로 탐색 시간대를 설정한다.
  • 마지막 목격 위치와 카메라의 실제 위·경도를 기준으로 초기 CCTV를 선택한다.
  • 설정된 조건은 사건별로 저장하여 녹화 영상 및 실시간 영상 탐색에 사용한다.
  • 시작·종료 시각은 함께 입력하거나 함께 비우며 종료가 시작보다 빠르면 저장하지 않는다. 탐색 구역은 선택 입력이다.
  • 전체 조건 편집은 `PUT`을 사용하여 제외 조건·시간·구역을 명시적으로 초기화할 수 있게 한다.
  • 탐색 중에는 마지막 실시간 사용 가능 조건과 마지막 활성 사건 카메라를 제거할 수 없으며, 종료 사건의 설정은 읽기 전용으로 표시한다.
  • 설정 카드에는 실시간 사용 가능 조건 수, 활성 배정 카메라 수와 탐색 시작 가능 여부를 표시하고 누락 영역으로 이동할 수 있게 한다.
  • 카메라 선택 화면은 전체 카메라 API의 검색·페이지네이션을 사용하고 코드, 이름, 위치, 미디어 서버와 연결 상태를 표시한다. 여러 대를 한 번에 추가할 수 있으며 `OFFLINE`·`ERROR` 카메라는 선택을 허용하되 경고한다.
  • 사건이 `SEARCHING`이면 조건·카메라 변경 커밋 후 실시간 검색 대상 변경 알림을 발행한다. 설정 변경은 녹화 분석 작업이나 outbox를 만들지 않는다.

4. 임베디드 검색 대상 동기화
  • 임베디드·실시간 처리기는 `GET /api/v1/device/search-targets`를 주기적으로 호출하여 최신 검색 대상 전체 스냅샷을 동기화한다.
  • 요청은 미디어 서버별 `X-Device-Key`로 인증하며, 인증된 미디어 서버가 소유한 카메라가 연결된 `SEARCHING` 사건만 반환한다.
  • 응답에는 사건 식별자, 사건번호, 실시간 사용 가능한 검색 조건(canonical prompt, 제외 조건, 탐색 시간대·구역)과 활성 검색 카메라를 포함한다.
  • Device snapshot에는 유사도 임계값을 포함하지 않으며 Jetson이 모델 버전에 맞는 자체 실행 설정으로 관리한다.
  • 종료된 사건, 비활성·삭제된 검색 조건과 카메라는 응답에서 제외한다.
  • 미디어 서버별 검색 대상 변경 버전으로 ETag를 생성하고, 디바이스가 `If-None-Match`를 보내 변경되지 않았으면 `304 Not Modified`를 반환한다.
  • 사건 종료나 검색 조건·카메라 삭제처럼 로컬 대상 제거가 필요한 변경도 전체 스냅샷으로 동기화하여 디바이스가 정확히 삭제할 수 있도록 한다.
  • 변경이 없는 응답은 `private, no-cache, must-revalidate` 정책으로 조건부 재검증을 허용하고, 검색 대상 데이터가 다른 디바이스·프록시로 공유되지 않도록 한다. |
| RE-SF4 | 녹화 CCTV 영상 기반 실종자 탐색 | 실종 예상 시각부터 현재까지의 녹화 영상에서 탐색 조건과 유사한 실종자 후보를 검색한다. |  1. 영상 저장
  • CCTV 영상을 H.264 형식으로 녹화한다. **(확인 필요**)**
  • FFmpeg를 사용하여 영상을 일정 시간 단위의 MP4 파일로 분할한다. **(몇분?)**
  • 영상 파일은 MinIO 객체 저장소에 저장한다.
  • CCTV 식별 정보, 촬영 시작·종료 시각, 파일 저장 경로 등의 영상 정보는 MySQL에 저장한다.

2. 녹화 업로드 순서
  • Raspberry Pi 5 미디어 서버는 공용 HTTPS Device API에서 `camera-01` 녹화의 서버 생성 object key와 15분 presigned PUT URL을 발급받는다.
  • 100 MiB 이하 MP4를 응답의 공용 HTTPS storage URL에 `Content-Type: video/mp4`로 단일 PUT한다.
  • 업로드 성공 후 같은 UUID·촬영 시간·서버 발급 object key로 녹화 완료 API를 호출한다.
  • 미디어 서버에는 MinIO 장기 자격증명을 배포하지 않는다. Tailscale은 dev MediaMTX HLS에만 사용한다.

3. 분석 대상 선정
  • 현재 제공 범위에서는 관리자가 녹화본과 탐색 조건을 선택해 녹화 분석 작업을 별도 등록한다.
  • 탐색 중 상태 변경은 실시간 검색 대상 알림만 발행하며 `analysis_jobs`나 녹화 분석 outbox를 자동 생성하지 않는다.
  • 마지막 목격 장소·시각을 기준으로 녹화 작업을 자동 등록하는 흐름은 후속 목표다.

4. 영상 분석
  • FFmpeg를 이용하여 녹화 영상에서 프레임을 추출한다.
  • 사람 검출 모델로 사람 영역을 추출한 후 CLIP 기반 모델로 탐색 조건과 유사도를 계산한다.
  • 추출된 사람 이미지와 사건별 사진·자연어 탐색 조건의 유사도를 CLIP 기반 모델로 계산한다.
  • AI Worker가 모델 버전에 맞춰 관리하는 내부 후보 선별 정책을 통과한 결과를 실종자 후보로 생성한다.
  • 임계값은 중앙 작업 요청·응답이나 작업 snapshot에 포함하지 않는다.
  • 연속된 프레임에서 동일하거나 유사한 사람이 반복 검출된 경우 하나의 후보로 통합한다.

5. 결과 저장
  • 후보 이미지와 탐지 전후 영상 클립은 MinIO 객체 저장소에 저장한다.
  • 사건 ID, CCTV 정보, 탐지 시각, 유사도, 탐지 출처와 파일 저장 경로를 MySQL에 저장한다.

6. 후속 작업 등록
  • AI Worker의 내부 선별 정책을 통과한 후보를 시간순으로 연결하여 관측 추정 경로를 구성한다.
  • 중앙 서버는 최근 경로와 카메라 위·경도를 기준으로 다음 예상 카메라를 최대 2대 선정한다.
  • 예상 도착 시각 전후의 녹화 구간을 AI Worker 분석 작업으로 등록한다. |
| RE-SF5 | 실시간 영상 기반 실종자 탐색 | 실시간 CCTV 영상에서 실종자와 유사한 후보를 탐지하고 관제실 관리자에게 알림을 제공한다. | 1. 영상 입력
  • Jetson 1대가 관할 카메라 4대의 RTSP 스트림을 입력받는다.
  • Jetson은 한 번에 한 사건의 인상착의만 탐색한다.
  • 입력 영상은 장치 성능에 맞게 FPS를 조정한다.
 
2.영상 전송 
  • CCTV(라즈베리파이&노트북) → Jetson : RTSP (실제 CCTV도 RTSP 사용)
  • Jetson → 서버 : REST API
  • 브라우저 → admin-dev Nginx : HTTPS `/media-stream/{cameraCode}`
  • admin-dev Nginx → Raspberry Pi 5 MediaMTX : Tailscale 비공개 경로의 HLS(TCP 8888)
  • 브라우저는 tailnet에 참여하지 않으며, RTSP와 후보 이벤트 REST API·Device Key 인증 경로는 기존 계약을 유지한다.
  • 이 Tailscale 영상 경로는 dev 환경에만 적용하며 master 구성은 변경하지 않는다.

3. 잿슨처리 
  • CLIP (이미지 인코더 구조를 그대로 가져와서 확장) - 필요에 따라 자체 데이터로 fine-tuning  
  • DH-ViT (지식 증류를 활용하여 CLIP기반의 자체 모델 구현) - 이미지 맥락을 이해하는 동시에 이미지로부터 추출 대상인 객체를 후처리하는 기능 추가 
  • OrinDH(TensorRT로 컴파일해서 Jetson에서 빠르게 돌게 최적화)

3.1 Jetson Orin Nano 개발환경
  • OS: Ubuntu (JetPack, Python 3.10.12)
  • 컨테이너: Docker (jetson-containers)
  • 실행 이미지: dustynv/nanoowl:r36.4.0
  • 모델: NanoOWL (OWL-ViT + TensorRT), CLIP (tree prediction용)
  • 엔진 파일: owl_image_encoder_patch32.engine
  • 데모: tree_demo.py (웹 UI, 포트 7860)

3.2 윈도우 PC 개발환경 
  • OS: Windows
  • 가상환경: venv (Python 3.12)
  • GPU: NVIDIA GeForce RTX 4070 Laptop GPU
  • CUDA: 13.1 (드라이버 기준, PyTorch는 cu130 빌드 사용)
  • PyTorch: 2.13.0+cu130
  • 주요 라이브러리: transformers, CLIP(OpenAI), opencv-python, jupyter, ipykernel

4. 정보 전송
  • 전송 조건 : AI 모델이 계산한 인상착의 유사도가 Jetson 내부 후보 선별 정책을 통과
  • 해당 임계값은 관리자 UI, Backend API 또는 Device snapshot에서 전달하지 않고 Jetson의 모델 실행 설정으로 관리
  • 전송 데이터
      ◦ 메타데이터 (JSON) : 탐지 시각, 카메라 식별자, Bounding Box 좌표
      ◦ 이미지 데이터 : 대상자의 크롭 이미지 파일

5. AI 후보 이벤트 표준화
  • Jetson에서 전송하는 후보 정보를 표준 AI 이벤트 형식으로 정의
      ◦ 후보 이벤트에는 이벤트 ID, 카메라 ID, 영상 촬영 시각 등의 정보를 포함
  • AI 모델과 백엔드가 동일한 JSON 필드명과 자료형을 사용하도록 메시지 명세를 작성

6. AI 후보 이벤트 검증 및 저장
  • 서버는 후보 이벤트를 수신한 후 다음 정보를 검증
      ◦ 존재하는 사건인지 여부
      ◦ 등록된 Jetson과 카메라에서 전송한 이벤트인지 여부
      ◦ 필수 데이터의 누락 여부 등

  • 통합 후보에는 최초 탐지 시각, 마지막 탐지 시각, 최고 유사도, 평균 유사도, 탐지 횟수와 `실시간 Jetson` 출처를 저장한다.

7. 실시간 후보 알림
  • 후보 이벤트의 검증과 데이터 저장이 완료되면 WebSocket과 STOMP를 통해 관제 대시보드에 실시간으로 전달
  • 관제 화면은 사건별 Topic을 구독하여 해당 사건의 후보 이벤트만 수신
  • 실시간 알림에는 후보 이미지, 탐지 시각, 카메라 정보, 위치와 유사도를 포함한다.
